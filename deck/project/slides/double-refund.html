Crash, resume, double refund

Replaying a write is how customers get paid twice

1

Model decides to refund. Checkpoint saved.

2

Refund executes. Money moves.

3

Worker crashes before the result is saved.

4

Resume replays the same tool call.

Without a key: 2 refunds in the ledger

Key = task + tool_call_id: 1 refund, same result returned

This is the most memorable demo of the block, and it is deterministic: FaultInjector with crash_after on issue_refund. The fix works because the checkpoint holds the assistant message with its tool_call id, so a replay carries the same id and therefore the same idempotency key. The payments service sees the key and returns the original result instead of paying again. The key is derived by the harness, never chosen by the model.
